01

Overview & mental model

Sentiva is a fictional consumer digital-safety brand (products: Shield, Alert, Family, ID, Scan). This solution gives Sentiva's product website a single HTTP endpoint it can call to answer end-customer questions — in the customer's own language — grounded in Sentiva's real documentation rather than the model's imagination.

The whole system is best understood as two flows that meet at one shared store:

  • Flow 1 — offline ingestion (built once, refreshed on demand): raw documents become a searchable knowledge base in Lakebase.
  • Flow 2 — online serving (runs on every question): the agent retrieves from that knowledge base and composes an answer.

The store where they meet is Lakebase (a serverless Postgres). Everything else — Unity Catalog, the Apps, the AI Gateway, the tracing tables — hangs off these two flows.

Flow 1 — Building the knowledge base

This is the offline pipeline: the Lakeflow job sentiva_ingest, a six-task DAG. Two document types (JSON and PDF) travel their own paths, converge into one chunk table, get embedded, and land in Lakebase. It runs once at setup and again whenever the content changes.

Generate source documents

Writes 48 multilingual product docs (JSON) and 3 datasheets (PDF) into the UC Volume. Idempotent — skips if content already exists. (In a real deployment this is where the customer's own content lands.)

generate_data.pyUC Volume · raw_docs
Load JSON → Delta (JSON path)

read_files() reads the JSON docs into the Delta table docs_json — structured columns for product, language, category, title, body, FAQs.

01_load_json.sqlDelta · docs_json
Chunk JSON (JSON path)

ai_prep_search(body) splits each doc into search chunks, then variant_explode flattens them into rows of docs_chunks. Each chunk carries two forms — one optimised for embedding, one to return to the reader.

ai_prep_search()02_chunk_json.sqlDelta · docs_chunks
Parse PDFs → Delta (PDF path)

ai_parse_document(content) runs OCR and layout parsing over the binary PDFs into docs_parsed; product and language are derived from the filename. This is the OCR showcase — a Japanese datasheet becomes searchable text.

ai_parse_document()03_parse_pdf.sqlDelta · docs_parsed
Chunk PDFs → same table (paths converge)

ai_prep_search(parsed) chunks the parsed PDFs and INSERTs them into the same docs_chunks table. From here, JSON- and PDF-sourced chunks are treated identically.

ai_prep_search()04_chunk_pdf.sqlDelta · docs_chunks
Embed & load into Lakebase

Reads docs_chunks, sends each chunk's embed-text to Qwen3-Embedding-0.6B (batched), and UPSERTs the row — text, 1024-d vector, metadata — into Lakebase kb.documents. Then it builds the two search indexes and ANALYZEs.

embed_and_load.pyQwen3 embeddingLakebase · kb.documents
End state: ~53 chunks in kb.documents, each with content, an embedding vector(1024), an auto-generated content_tsv keyword column, and two indexes — lakebase_ann (semantic) and lakebase_bm25 (keyword). The knowledge base is ready to serve.
04

Flow 2 — Answering a question

This is the online path, and it runs on every question. It is a tool-calling agent: the model itself decides to look something up, reads the results, then answers — streaming the reply token by token so the first words appear in ~1–2 seconds.

The product site asks

A visitor asks a question on Sentiva's site (simulated by App B). App B posts { session_id, message } and opens a streaming connection to the agent.

App B · sentiva-web
App B forwards to the agent

App B is the customer's web tier. It forwards the user's identity token and calls App A's standard /responses endpoint, translating the stream back into the shape its React UI expects.

→ App A · /responses
The agent decides to search

MLflow AgentServer hands the request to the LangGraph agent. The LLM (via the Gateway) chooses to call the search_knowledge_base tool with a query it forms from the question.

MLflow AgentServercreate_react_agent
Hybrid retrieval from Lakebase

The tool embeds the query (Qwen3) and runs Lakebase Search: a vector search (lakebase_ann) unioned with a keyword search (lakebase_bm25), then deduped by relevance — returning the top passages plus their source metadata.

Lakebase · kb.documentsvector + keyword
The LLM composes the answer

The retrieved passages go back to the model — through the Unity AI Gateway, which meters usage and logs the payload. The model answers using only those passages, in the question's language. Prior turns come from Lakebase memory.

Unity AI Gateway → LLMmem.chat_history
Stream back, remember, and trace

Answer tokens stream to the browser as they're generated; a final event carries the source cards and per-step timings. The turn is saved to memory, and the whole request — retrieval + LLM spans — is written to the MLflow OpenTelemetry trace tables in Unity Catalog.

SSE stream → UIMLflow OTel → UC
Why tool-calling, not a fixed pipeline? The agent could be wired to always retrieve. Making retrieval a tool the model invokes is the pattern that scales to real agents — more tools, multi-step reasoning — without changing the serving layer. It is the Databricks-recommended shape for an agent on Apps.
05

Key components, in depth

Five components carry the weight of this solution. Each is a first-class Databricks capability chosen for a specific job.

Lakebase Search — the knowledge base

Lakebase is serverless Postgres. Lakebase Search adds two index types on top: lakebase_ann for semantic vector similarity (pgvector under the hood) and lakebase_bm25 for keyword relevance over a generated content_tsv column. Retrieval is hybrid — vector and keyword results merged — so a question phrased differently from the docs still hits, while exact terms (product names, prices) still rank. One Postgres holds both the knowledge base and the agent's memory.

Unity AI Gateway — the LLM front door

The agent never calls a model endpoint directly. It calls a Unity AI Gateway model-service (dbx_agent_lakebase.rag.sentiva_llm) whose routing destination points at the actual foundation model. This gives three things for free: governed routing (swap the model without touching agent code), usage tracking, and an inference table that logs every request/response payload into Unity Catalog.

MLflow AgentServer — the serving layer

App A does not hand-roll a web server. It uses MLflow AgentServer (databricks-agents) — an async FastAPI server that provides the standard endpoints (/responses, /invocations, /health), streaming, and tracing hooks. The agent is written as MLflow @invoke/@stream handlers over the ResponsesAgent interface. This is the platform's paved path for authoring an agent and deploying it on Databricks Apps.

MLflow tracing in OpenTelemetry format

Every request is traced. Because the MLflow experiment is bound to a Unity Catalog trace location, spans land as governed Delta tables in OpenTelemetry format — *_otel_spans and companions — alongside higher-level per-trace views. Each trace shows the retrieval and ChatDatabricks steps with timing, which the AI/BI dashboard reads directly.

Agent memory in Lakebase

Multi-turn context is kept in mem.chat_history, keyed by session_id. On each turn the agent loads recent history and, after answering, appends the new exchange — so follow-ups like "which of those plans includes a VPN?" resolve against the earlier turn.

Deploy, configure, tear down

The entire solution targets a fresh workspace by editing one file, config.env, and running ordered stages. Two steps must be enabled once in the workspace UI (they have no CLI); a state-aware preflight verifies them.

Stages, in order

Configure

setup_config.sh fills config.env; preflight.sh checks tools, auth, warehouse, models.

Bootstrap

bootstrap.sh creates the catalog and a fresh Lakebase project.

UI toggles

Enable Lakebase Search on the project and the AI Prep Search preview.

Search init

bootstrap_search.sh installs extensions and creates the kb/mem schemas.

Deploy

deploy.sh ships the bundle, creates the Gateway service, grants the app, and starts both Apps.

Ingest

Run sentiva_ingest to populate the knowledge base.

Configure & swap the model

The agent always calls the Gateway service by name, so the model is chosen at the Gateway, not in code. To switch models:

# 1 — verify it can drive the tool-calling agent
./scripts/test_model.sh \
   databricks-claude-opus-4-8

# 2 — set it and recreate the gateway
LLM_ENDPOINT=databricks-…
./scripts/create_gateway.sh

No agent or UI code changes. Verified swappable to deepseek, Claude, and GLM; reasoning models are rejected by the probe.

Tear down cleanly

Cost is bounded by teardown: teardown.sh destroys the bundle resources, the Gateway service, the inference table, the Lakebase project, and the MLflow experiment; verify_teardown.sh confirms nothing billable remains.

08

Design decisions & trade-offs

The choices below are the ones a first-time reader most often asks about.

AgentServer over a hand-rolled server

Serving, streaming, and trace wiring are things the platform provides. Using MLflow AgentServer means none of that is hand-written — the "best practice" is that you don't build it yourself. The trade-off is a heavier dependency stack, pinned to a known-good set.

Hybrid retrieval, not vector-only

Pure vector search misses exact terms (a product name, a price); pure keyword search misses paraphrases. Running both and merging is more robust for a product-support corpus — and Lakebase gives both in one store.

A non-reasoning model for the tool loop

Tool-calling requires the model's tool-call format to survive a round-trip through the Gateway. Reasoning models (Gemini 2.5/3.x, GPT-5.x) don't, so the default is a fast non-reasoning model. The Gateway keeps this a config choice, not a code change.

React UI kept behind a stable contract

App A speaks the standard /responses protocol; App B translates it to the simple {token} / {done} stream the React UI consumes. The web tier absorbs the protocol, exactly as a real product website would — so the UI stays simple and stable.

Teardown completeness

Some objects live outside the bundle — the Gateway service, the inference table, the Lakebase project, and the MLflow experiment (which lives in the workspace, not the catalog). Teardown removes all of them, and a stale experiment is deleted specifically so the next deploy re-creates its trace tables cleanly.
